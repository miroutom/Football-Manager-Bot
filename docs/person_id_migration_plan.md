# План: `person_id` — стабильный ключ игрока

Цель: **один человек = один `person_id` на всё время проекта**.  
`id` строки SQLite остаётся «эпизод в клубе»; **`person_id` — ключ переноса статы между клубами, сезонами и в `*_synced.db`**.

Имена вроде «Мартинез» и «Альварес Мартинез» — разные `person_id`, слияние по фамилии больше не нужно для карьерной агрегации.

---

## 1. Модель данных

### 1.1 Реестр (источник истины для выдачи id)

Файл: **`db/players_registry.db`** (отдельный sqlite, не сезонный).

| Таблица | Поля | Назначение |
|---------|------|------------|
| `persons` | `person_id` PK, `created_at`, `notes` | Человек в проекте |
| `person_aliases` (опц.) | `person_id`, `name`, `team` | Поиск / ручные алиасы после переименований |

**Выдача id:** монотонный счётчик `person_id = MAX(person_id) + 1`, **никогда не переиспользуем**.  
Старт с **1**; при backfill существующим игрокам назначаем пакетно, счётчик поднимаем до max.

Утилита: `utils/person_registry.py`

- `allocate_person_id() -> int`
- `register_person(notes="") -> int`
- `get_person_ids_for_name(team, name)` — опционально, для отладки

### 1.2 Колонка в игровых таблицах

Во всех ORM-моделях (`Forward`, `Midfielder`, `Defender`, `Goalkeeper`):

```text
person_id = Column(Integer, nullable=True, index=True)
```

**Nullable** на переходный период: старые строки без id → агрегаторы fallback на текущие эвристики (имя/фамилия).

Где должна быть колонка (одинаковая схема):

| Хранилище | Файлы |
|-----------|--------|
| Активный сезон | `db/season_{N}/league.db`, `champions_league.db`, `common.db` |
| Архивы | `db/season_1/*`, `db/season_2/*`, … |
| Накопление | `db/league_synced.db`, `champions_league_synced.db`, `common_synced.db` |

Миграция схемы: `scripts/migrate_add_person_id_column.py` (ALTER TABLE для всех перечисленных файлов, если файл есть).

### 1.3 Семантика полей

| Событие | `id` (строка) | `person_id` |
|---------|----------------|-------------|
| Правка имени/рейтинга/позиции/нации в клубе | тот же | тот же |
| Трансфер | новая строка | **копия с донора** |
| Новый игрок в клуб | новая строка | **новый** из реестра |
| Уход (`left_team=True`) | старая строка | тот же |
| Завершение сезона → архив | копия снимка | **без изменений** в строках |
| Сезон N → N+1 (тот же человек в заявке S2) | новая строка в S2 | **тот же person_id**, что в S1 |

## 2. Правила агрегации (замена эвристик)

### 2.1 Ключи слияния

| Режим | Старый ключ | Новый ключ |
|-------|-------------|------------|
| `common` (лига+ЛЧ в клубе) | фамилия + клуб + позиция | **`person_id` + клуб + позиция** (fallback: старый `_key`) |
| Сезон: «все чемпионаты» / `allcl` | имя + позиция | **`person_id`** (две строки одного человека в сезоне → одна в топе) |
| Сезон: одна нац. лига | обычно без merge | по клубу в БД; при merge — **`person_id` + лига** |
| `*_synced` при дописывании сезона | фамилия + позиция | **`person_id` + позиция** (клуб обновляется из более нового сезона) |
| Топ-100 / за всё время | фамилия + позиция | **`person_id` + позиция**; клуб = активный сезон |

Выбор «последнего клуба» в сезоне: среди строк с одним `person_id` — max `matches`, затем max `id` (как сейчас `latest_row`).

### 2.2 Файлы кода

| Модуль | Изменение |
|--------|-----------|
| `utils/person_registry.py` | новый |
| `utils/player_transfer.py` | `_insert_fresh_row_at_team`: копировать `person_id`; add: `allocate` |
| `utils/squad_roster_sync.py`, `utils/roster_manual.py` | правки в клубе: не трогать `person_id` |
| `utils/common_db.py` | `_key()` → `person_id` при наличии |
| `utils/cumulative_db.py` | `_find_row_by_identity` → `_find_row_by_person_id` + fallback |
| `utils/stats_history_agg.py` | `_bucket_key_for_row` → `person_id` при наличии |
| `utils/cumulative_mirror.py` | зеркало трансферов: тот же `person_id` в synced |
| `data/*.py` | колонка `person_id` |

Документировать в `docs/stats_menu_rules_full.md` § «Идентичность игрока».

## 3. Пошаговая реализация

### Фаза 0 — подготовка (без изменения бота)

1. Добавить `person_id` в модели + скрипт миграции схемы всех sqlite.
2. Создать `players_registry.db` и `utils/person_registry.py`.
3. Dry-run отчёт: сколько строк в S1/S2/active без колонки (ожидаемо: все, пока NULL).

**Критерий готовности:** `migrate_add_person_id_column.py` проходит на локальной копии `db/`, бот ещё не зависит от поля.

---

### Фаза 1 — реестр и активный сезон (runtime)

**Цель:** все **новые** операции сразу получают `person_id`; трансферы не рвут цепочку.

1. **Добавление игрока** (`add_player_to_club`, бот):  
   `person_id = allocate_person_id()` → league + cl (+ после rebuild common).

2. **Трансфер** (`_insert_fresh_row_at_team`):  
   `person_id = getattr(donor, "person_id")` или, если у донора NULL, один раз выделить и **записать обратно в донора** (закрыть дыру на старых строках).

3. **Переименование / смена позиции в клубе** (`rewrite_team_player_identity`, merge в боте):  
   `person_id` не менять; при слиянии двух строк одного клуба — один `person_id` у keeper, donors удалить.

4. **`rebuild_common_database`**: ключ бакета с `person_id`.

5. **`cumulative_mirror`**: при зеркале трансфера/добавления в `*_synced` — тот же `person_id`.

6. Тесты/проверка:
   - трансфер Мартинез Интер→другой клуб: две строки, один `person_id`;
   - новый Альварес Мартинез в Сассуоло: другой `person_id`.

**Критерий:** в активном `season_2` (или текущем) все строки с матчами > 0 после ручного прогона assign имеют NOT NULL `person_id` для игроков из заявки.

---

### Фаза 2 — backfill активного сезона + common

Скрипт: **`scripts/assign_person_ids_active_season.py`**

Порядок:

1. Загрузить все строки из `league.db` + `champions_league.db` активного сезона (4 таблицы × 2 файла).
2. Группы «один человек сейчас»:
   - уже есть `person_id` → в группу;
   - иначе эвристика: **(норм. имя, позиция, клуб)** для активных; для `left_team` — привязать к активной строке того же **(имя, позиция)** в другом клубе если матчи на left и 0 на новой (типичный трансфер).
3. Каждой группе — один `allocate` или существующий id.
4. Проставить во все связанные строки (league, cl, затем `rebuild_common`).
5. Отчёт CSV: `row_id, name, team, person_id, rule`.

**Не склеивать** пары вроде Мартинез / Альварес Мартинез даже при одной позиции — разные полные имена → разные группы (явное правило в скрипте).

**Критерий:** 0 конфликтов «два разных человека → один person_id» в review-отчёте.

**Скрипт (реализовано):**

```bash
# 1) Отчёт без записи в БД
python3 scripts/assign_person_ids_active_season.py

# 2) Проверить data/person_id_active_season_review.csv и needs_review в JSON
# 3) При необходимости: data/person_id_active_overrides.json (см. example)
python3 scripts/assign_person_ids_active_season.py --apply
```

Трансфер (Тонали Ньюкасл left + Сити active, разные позиции) → ``transfer_same_name``.  
Несколько активных клубов с одним именем → ``needs_review``, не склеивать без overrides.

---

### Фаза 3 — архив season_1 (историческая правда)

Скрипт: **`scripts/assign_person_ids_season_archive.py --season 1`**

1. Прочитать `season_1/league.db` + `cl.db`.
2. Для каждой строки с матчами/статой:
   - если в реестре уже есть игрок с тем же **полным именем + позиция + клуб** из фазы 2 → взять его `person_id`;
   - иначе отдельная эвристика + ручной CSV `overrides_season1.csv` (`season,table,row_id,person_id`).
3. Записать в `season_1/league.db`, `season_1/cl.db`, пересобрать `season_1/common.db`.
4. Валидация: топ Г+А сезона 1 по `person_id` = Мартинез Интер 56+8, не Сассуоло.

**Критерий:** ключевые игроки из скриншотов/топов совпадают; спорные строки только в `overrides_*.csv`.

---

### Фаза 4 — стыковка season_1 ↔ season_2 (главное для вас)

Скрипт: **`scripts/link_person_ids_cross_season.py`**

Вход: `season_1/league.db`, `season_2/league.db` (+ опц. cl).

**Автоматический матч «продолжение карьеры»** (скоринг, порог принятия):

| Сигнал | Вес |
|--------|-----|
| Одинаковый `person_id` уже проставлен в S2 | стоп, ок |
| Полное имя (casefold) + позиция | высокий |
| Фамилия + позиция + тот же клуб в S2 | средний |
| Близкая стата (|Δgoals|+|Δassists| ≤ 2) при том же клубе | средний |
| Только фамилия + позиция | **низкий, не автопринять** |

Алгоритм:

1. Построить множество `person_id` из S1 (после фазы 3).
2. Для каждой строки S2 **без** `person_id`:
   - кандидаты из S1 с тем же именем/позицией;
   - если ровно один кандидат с score ≥ порога → присвоить **S1.person_id**;
   - иначе → `pending_cross_season.csv`.
3. Строки S2 **новые лица** (нет матча) → `allocate_person_id()`.
4. Синхронизировать `season_2/cl.db` и `common.db` по `(person_id, team, position)`.
5. Итоговый отчёт: `linked`, `new_person`, `manual_required`.

**Ручной этап (обязателен):** правка `data/person_id_cross_season_overrides.json`:

```json
{
  "season_2": {
    "league:forwards:123": 118,
    "league:forwards:155": 901
  }
}
```

Повторный прогон с `--apply-overrides`.

**Критерий:** каждый игрок из заявки S2, игравший в S1, имеет **тот же** `person_id`; новички S2 — новые id.

---

### Фаза 5 — пересборка `*_synced` по `person_id`

1. Бэкап `db/*.db`.
2. **`scripts/rebuild_league_synced_from_archives.py`** — доработать merge в `cumulative_db` на `person_id`.
3. Либо полная пересборка synced с нуля из `season_1` + `season_2` (предпочтительно после фаз 3–4).
4. Проверка:
   - топ-100 Г+А = сумма по `person_id` за архивы;
   - «стата сезонов» S1/S2 без склейки однофамильцев.

**Критерий:** `aggregate_life_outfield` и `format_season_stat` используют только `person_id` там, где поле заполнено.

---

### Фаза 6 — бот и отключение fallback

1. Агрегаторы: если **все** строки в выборке имеют `person_id`, не использовать фамилию.
2. Лог при NULL: warning в админ-канал / лог файл.
3. Опционально: NOT NULL constraint после аудита.

**Критерий:** нет NULL в активном сезоне и в synced для игроков с матчами.

---

## 4. Завершение сезона (будущее)

При `season_end` / архивации:

1. Снимок `season_N/*.db` уже содержит `person_id` — **ничего не пересчитывать**.
2. `append_season_snapshot_to_all_time`: merge в synced по **`person_id` + позиция** (не по фамилии).
3. Новый сезон N+1: при копировании заявки скрипт **`carry_person_ids_to_new_season.py`**:
   - матч S(N+1) roster ↔ S(N) по заявке бота / (имя, позиция, клуб);
   - перенос `person_id` на новые строки с нулевой статой.

## 5. Риски и как их закрыть

| Риск | Митигация |
|------|-----------|
| Склейка однофамильцев | Автомат только при **полном имени**; фамилия — manual |
| Два `person_id` у одного человека | Скрипт `dedupe_person_ids.py`: merge stats → keeper, reassign rows |
| Рассинхрон VPS / локаль | Деплой: миграция схемы → скрипты → rebuild synced; один коммит данных `db/` или выгрузка registry |
| Старые трансферы без id на доноре | При трансфере: backfill donor; скрипт фазы 2 |
| Игрок удалён и заведён заново | По умолчанию **новый** `person_id`; override в JSON при «тот же человек» |

## 6. Порядок работ (краткий чеклист)

```text
[ ] Фаза 0: колонка + registry + migrate script
[ ] Фаза 1: transfer / add / common / mirror
[ ] Фаза 2: assign active season
[ ] Фаза 3: assign season_1 archive
[ ] Фаза 4: link S1→S2 + overrides CSV/JSON
[ ] Фаза 5: rebuild *_synced
[ ] Фаза 6: stats_history_agg + docs + убрать fallback
[ ] VPS: backup → pull → scripts → restart bot
```

Оценка: **фазы 0–1** — один PR (код, без массового backfill); **фазы 2–5** — второй PR (скрипты + прогон на копии `db/` + review CSV); **фаза 6** — после проверки топов в боте.

---

## 7. Что не делаем

- Не заменяем `id` строки на `person_id` в UI бота (в заявке по-прежнему можно показывать имя; внутренне — `person_id` для merge).
- Не используем «ordinal 0..N по заявке» — только монотонный `person_id` из реестра.
- Не меняем правило «трансфер = новая строка, стата у старого клуба» — меняется только **ключ склейки** для отчётов и synced.
